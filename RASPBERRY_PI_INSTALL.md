# Raspberry Pi camera application

Use 64-bit Raspberry Pi OS on a Pi 5 with 2 GB RAM. Install the app and its Python dependencies in `~/securitycamera/.venv`. Keep the model files and `.env` on the device; never copy `.env`, RTSP addresses containing credentials, or camera passwords into diagnostic exports or support messages. The web console listens on port 8080. Keep it on a trusted network: the console itself does not provide user authentication.

Configure the device's API URL, device ID and device token in `.env`. Set `OBJECT_DETECTION_ENABLED=true` and supply the models required by the configured detector. Set `WHATSAPP_OBJECT_ALERTS_ENABLED=true` only when recipients and the API are configured. Detection scenarios are currently two or more confirmed people at any time, or one confirmed person from 21:00 to 05:00 in the configured scenario timezone. A motion crop must first pass the moving-object gate. Detection is probabilistic; measure results separately for every camera and lighting condition.

Select up to four cameras in the console and set sensitivity and exclusion areas individually. Selected cameras are stored privately under `~/.local/state/securitycamera/cameras.json` and restored after a process restart. The file contains camera credentials and must remain private to the Pi user. Stop a camera in the console if it should not restart. The web service template is `deploy/systemd/security-camera-web-user.service`; install it under `~/.config/systemd/user/`, enable lingering using `loginctl enable-linger`, and enable the service only after stopping any existing instance. Never run both the old headless detector and the web app for the same cameras.

For remote support, enable Raspberry Pi Connect and link it to the owner's Raspberry Pi account with `rpi-connect signin`. Keep lingering enabled so remote shell works after reboot. Follow the official Raspberry Pi Connect documentation for account linking and troubleshooting.

## Archive and review

Install and verify the API archive endpoints and the `011_create_media_archive.sql` migration before setting `MEDIA_ARCHIVE_ENABLED=true`. A single background worker archives completed motion clips, object clips, and detection images. It streams files and asks the API to check the Azure blob's stored size and MD5 before deleting an unchanged local file. Its SQLite queue survives a restart and retries failures; local files stay in place if upload or verification fails. Detection metadata is stored in SQL with the media record. An interrupted recording is marked as such on the next startup.

An object clip with an alert is retained locally until the alert receives an affirmative API result. If the send fails or is interrupted, the outcome may be unknown and the clip is retained for investigation rather than blindly resending a possible duplicate. A provider's acceptance does not prove delivery to a phone. The console shows archive and alert warnings, cloud media and review buttons. Download the diagnostics bundle from the console for support; it omits connection settings and links and redacts common credentials. Review exports before sharing, because detection data and camera labels can still be sensitive.

The archive requires a network connection and Azure/API capacity. Existing files remain on the Pi while uploads are pending. At the motion clip limit, motion recording pauses but object detection continues. Low free disk space can prevent both motion and object recordings and consequently prevent clip-based alerts. Monitor health warnings and disk space; the archive is not a substitute for backups or a retention policy.

Use independent footage when evaluating misses: motion-triggered clips alone cannot show events for which motion never triggered. Save representative footage from each new camera in day, night, rain, glare and low-quality stream conditions. Manually label people and vehicles and review both false alarms and missed events before adjusting sensitivity or training a model.

## Test an image or clip

In **Test an image or clip**, select a running camera, enter the original recording date and time in South Africa time, choose a starting step and select a video up to 250 MB or a JPG/PNG image up to 25 MB. Motion starts the same live motion, object and scenario stages with the camera's sensitivity, detection method and exclusions. A single image cannot provide motion: choose object or scenario instead. Both use the shared full-frame detector and normal person-scenario rules without a moving-object gate; scenario testing needs object detection as its input. The entered recording time drives time-of-day rules; the app does not read the timestamp printed on the picture.

Videos run at recording speed and share the live object detector, including its person verifier, so live processing can slow during a test. When starting at motion, the first five seconds are used to warm up motion detection. Results show the checks, detected objects, matched rules and evidence images. At most 100 annotated images are saved per full-frame test, with a two-second spacing except for scenario matches. Tests never send WhatsApp notifications. Test files remain on the Pi in `~/SecurityCamera/clip_tests`, outside the live archive. The latest result remains accessible after an app restart; a test interrupted by a restart is marked incomplete.
